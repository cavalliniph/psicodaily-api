# Filtros de abordagem, modalidade e avaliação na busca de profissionais

> Escopo: **somente este repositório (psicodaily-api)**. Nada aqui altera outro projeto.

## Contexto
O cliente da busca de profissionais já envia `abordagem`, `modalidade` e `avaliacao_min` para `GET /api/profissionais/`. Hoje a API ignora esses parâmetros: não existe coluna de abordagem nem de modalidade em `PROFISSIONAL`, não existe tabela de avaliações, e a resposta não traz esses campos. O cliente esconde os filtros enquanto a resposta não trouxer `abordagem`, `modalidade` ou `avaliacao`, então eles passam a funcionar assim que a API devolver esses campos.

Objetivo: a API passa a armazenar, filtrar e devolver abordagem, modalidade e avaliação média.

**Contrato esperado pelo cliente** (nomes exatos, em minúsculas, como já sai do `cursor.description`):
- Query string: `abordagem` (ex.: `TCC`, `Psicanálise`), `modalidade` (`Online` | `Presencial`), `avaliacao_min` (`3`, `4`, `4.5`, `5`).
- Campos em cada profissional: `especialidade`, `abordagem`, `modalidade`, `avaliacao` (número com 1 casa ou `null`) e `total_avaliacoes`.

## Decisão de produto antes de começar
Hoje toda sessão é por vídeo (`SESSAO.LINK_REUNIAO`, signaling WebRTC). "Presencial" exigiria endereço e outro fluxo de agendamento. **Confirmar com o time se modalidade entra.** Se não entrar, pular todos os itens marcados com *(modalidade)*: o cliente já esconde esse filtro quando o campo não vem na resposta.

## Passos

### 1. Schema (`database/schema.sql` + banco local)
Não há migrações. Atualizar o `schema.sql` **e** rodar os `ALTER`/`CREATE` no `database/BANCO.FDB` (isql ou FlameRobin), porque o banco é versionado no repo e embutido no Docker.

```sql
CREATE DOMAIN dm_modalidade AS VARCHAR(20)
CHECK (VALUE IN ('ONLINE', 'PRESENCIAL', 'AMBAS'));          -- (modalidade)

ALTER TABLE PROFISSIONAL ADD ABORDAGEM VARCHAR(100);
ALTER TABLE PROFISSIONAL ADD MODALIDADE DM_MODALIDADE;        -- (modalidade)

CREATE TABLE AVALIACAO (
    AVALIACAO_ID INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    SESSAO_ID INTEGER NOT NULL,
    PACIENTE_ID INTEGER NOT NULL,
    PROFISSIONAL_ID INTEGER NOT NULL,
    NOTA SMALLINT NOT NULL CHECK (NOTA BETWEEN 1 AND 5),
    COMENTARIO VARCHAR(500),
    CRIADO_EM TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT UQ_AVALIACAO_SESSAO UNIQUE (SESSAO_ID),
    CONSTRAINT FK_AVALIACAO_SESSAO FOREIGN KEY (SESSAO_ID) REFERENCES SESSAO (SESSAO_ID) ON DELETE CASCADE,
    CONSTRAINT FK_AVALIACAO_PACIENTE FOREIGN KEY (PACIENTE_ID) REFERENCES USUARIO (ID_USUARIO) ON DELETE CASCADE,
    CONSTRAINT FK_AVALIACAO_PROFISSIONAL FOREIGN KEY (PROFISSIONAL_ID) REFERENCES PROFISSIONAL (USUARIO_ID) ON DELETE CASCADE
);
CREATE INDEX IX_AVALIACAO_PROFISSIONAL ON AVALIACAO (PROFISSIONAL_ID);
```
Os dois campos novos de `PROFISSIONAL` são opcionais (`NULL`), para não quebrar os profissionais já cadastrados.

### 2. Constantes e normalizadores (`funcao.py`)
Ao lado de `ESPECIALIDADES_PROFISSIONAIS`:
```python
ABORDAGENS = ["TCC", "Psicanálise", "Humanista", "Gestalt", "Comportamental"]
MODALIDADES = {"ONLINE", "PRESENCIAL", "AMBAS"}  # (modalidade)
```
- Criar um helper `normalizar_abordagem(valor)` que devolve o nome canônico de `ABORDAGENS`, comparando com `normalizar_texto` (igual ao `next(...)` de especialidade em `view/profissionais.py`), ou `None`.
- Criar `normalizar_modalidade(valor)` que devolve `normalizar_texto(valor)` se estiver em `MODALIDADES`, senão `None`. *(modalidade)*
- Os dois helpers servem para a listagem, o cadastro e o `PATCH /me`. Não duplicar o `next(...)` em cada rota.

### 3. `GET /api/profissionais/` (`view/profissionais.py::profissionais`)
**Parâmetros novos** (validados junto com os atuais, antes de abrir conexão):
- `abordagem`: `normalizar_abordagem`; se der inválido, `resposta_erro('Abordagem invalida')`.
- `modalidade`: `normalizar_modalidade`; se der inválido, `resposta_erro('Modalidade deve ser Online ou Presencial')`. *(modalidade)*
- `avaliacao_min`: `float`, de 1 a 5; fora disso, 400. Não usar o laço de inteiros existente, porque aceita `4.5`.

**SQL:**
- No `filtros`, juntar a média por um `LEFT JOIN` em tabela derivada (evita `GROUP BY` com `DESCRICAO` BLOB). Como o `COUNT(*)` reutiliza `filtros`, o join precisa ficar dentro dele:
  ```sql
  FROM PROFISSIONAL p
  INNER JOIN USUARIO u ON u.ID_USUARIO = p.USUARIO_ID
  LEFT JOIN (
      SELECT PROFISSIONAL_ID,
             AVG(CAST(NOTA AS NUMERIC(5,2))) AS MEDIA,
             COUNT(*) AS TOTAL
      FROM AVALIACAO GROUP BY PROFISSIONAL_ID
  ) a ON a.PROFISSIONAL_ID = p.USUARIO_ID
  WHERE u.ATIVO = TRUE
  ```
  O `CAST` é obrigatório: no Firebird, `AVG` de `SMALLINT` trunca para inteiro.
- Filtros:
  - `abordagem`: `AND p.ABORDAGEM = ?`
  - `modalidade`: `AND p.MODALIDADE IN (?, 'AMBAS')`. Quem atende nos dois casa com qualquer filtro. *(modalidade)*
  - `avaliacao_min`: `AND a.MEDIA >= ?`. Sem avaliação (`NULL`), o profissional fica de fora, e esse é o comportamento desejado.
- No `SELECT`, acrescentar `p.ESPECIALIDADE`, `p.ABORDAGEM`, `p.MODALIDADE`, `a.MEDIA AS AVALIACAO` e `COALESCE(a.TOTAL, 0) AS TOTAL_AVALIACOES`.

**Serialização:** o `fdb` devolve `NUMERIC` como `Decimal`. No laço que já monta `foto_url`, converter com `profissional['avaliacao'] = round(float(v), 1) if v is not None else None`, para sair como número no JSON e não como string.

### 4. `GET /api/profissionais/<id>` (`profissional`)
Mesmos campos novos do passo 3 e mesmo `LEFT JOIN`, com a mesma conversão de `avaliacao`. Extrair o trecho `SELECT ... FROM ... LEFT JOIN` para uma constante do módulo usada pelas duas rotas, para não duplicar SQL.

### 5. Cadastro (`POST /api/profissionais/`, `cadastro_profissional`)
- Ler `abordagem` e `modalidade` (`obter_campo`), ambos **opcionais**.
- Se vier preenchido e inválido, `resposta_erro`.
- Incluir as colunas no `INSERT` e no JSON de resposta.

### 6. Atualização (`PATCH /api/profissionais/me`, `atualizar_profissional`)
- Conjunto permitido passa de `{'descricao', 'preco_hora'}` para `{'descricao', 'preco_hora', 'abordagem', 'modalidade'}`. Atualizar a mensagem de erro.
- `abordagem`/`modalidade`: string vazia ou `null` limpa a coluna (`NULL`); valor inválido devolve 400; valor válido vai para `atualizacoes['ABORDAGEM']` / `atualizacoes['MODALIDADE']`.

### 7. Avaliar uma sessão (`view/consultas.py`)
Nova rota: `POST /api/consultas/<int:sessao_id>/avaliacao`, com `@usuario_autenticado`.
- Só `usuario_role == 'PACIENTE'`; outros papéis recebem 403.
- Corpo JSON permitido: `{'nota', 'comentario'}`; campos desconhecidos dão 400 (regra do CLAUDE.md). `nota` é `int` de 1 a 5, sem aceitar `bool`. `comentario` é opcional, string de até 500 caracteres após `strip()`.
- `SELECT PROFISSIONAL_ID, STATUS FROM SESSAO WHERE SESSAO_ID = ? AND PACIENTE_ID = ?`, usando o `id_usuario` **do token**. Se não achar, 404. Se `STATUS <> 'REALIZADO'`, 409 "Só é possível avaliar sessões realizadas".
- `INSERT INTO AVALIACAO ...` e `commit`. Se a constraint `UQ_AVALIACAO_SESSAO` for violada (`fdb.DatabaseError` com o nome dela na mensagem), 409 "Sessão já avaliada".
- Resposta 201: `{'message': ..., 'avaliacao': {'sessao_id', 'nota'}}`.

Em `GET /api/consultas/`, acrescentar `LEFT JOIN AVALIACAO av ON av.SESSAO_ID = s.SESSAO_ID` e o campo `av.NOTA AS NOTA_AVALIACAO`, para quem consome saber se a sessão já foi avaliada.

## Verificação
Sem framework de testes. Com `.venv\Scripts\python app.py` (porta 5000) e o Firebird no ar:

1. `curl "http://localhost:5000/api/profissionais/?page_size=100"`: cada item tem `especialidade`, `abordagem`, `modalidade`, `avaliacao` (`null` ou número) e `total_avaliacoes`.
2. Com `PATCH /api/profissionais/me` (cookie de um profissional), gravar `{"abordagem": "tcc", "modalidade": "online"}`. O `GET` deve devolver `"TCC"` / `"ONLINE"`. `{"abordagem": "xyz"}` dá 400.
3. Filtros: `?abordagem=TCC` traz só ele; `?abordagem=xyz` dá 400; `?modalidade=Online` inclui `ONLINE` e `AMBAS`; `?avaliacao_min=6` dá 400.
4. Avaliação:
   - Paciente avalia uma sessão `REALIZADO` própria: 201. A segunda vez dá 409.
   - Sessão `AGENDADO` dá 409, sessão de outro paciente dá 404, profissional dá 403, `nota: 6` ou campo extra dá 400.
   - Depois de avaliar, `?avaliacao_min=4` inclui ou exclui o profissional conforme a média, e `avaliacao` aparece com 1 casa.
5. Os filtros antigos continuam iguais: `preco_max=15000` (centavos), `disponibilidade_inicio/fim` e `especialidade`.
6. `python tests/test_pool.py` continua passando (o pool não muda, mas confirma que o banco abre com o schema novo).
